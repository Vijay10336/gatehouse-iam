# Your administrator account and application onboarding

## How the administrator signs in

Use the same Sign in page as other users. In the current local setup, the initial administrator is `admin@gatehouse.local`. Its initial password is the `BOOTSTRAP_ADMIN_PASSWORD` value in the local `.env` file generated by `scripts/setup.py`.

After authentication, the server checks the directory administrator flag. Administrators see the management console. Standard accounts see their account page and can sign in to registered applications.

The first administrator is initialized once per database. Changing bootstrap settings after initialization preserves the existing administrator configuration. Password changes take place through My account or the password reset flow.

For a fresh deployment, set `BOOTSTRAP_ADMIN_EMAIL` to your own email before starting the database/app for the first time. Use a unique password and configure your actual SMTP provider for account recovery.

## Keep administrator access limited to yourself

1. Open **Users** and enable **Administrators only**.
2. Review every returned account. There should be one administrator account if you want sole administrative access.
3. Leave **Directory administrator** off for other users. Application roles such as `viewer` and `editor` control application permissions separately.
4. Remove the administrator flag from any account that should lose management access. Saving a user change revokes that user's sessions and OAuth grants.
5. Use **My account → Change password** to set a unique password for your account. Keep `.env` and database/hosting credentials private and outside source control.

The final enabled, verified administrator cannot remove or disable their own administrative access. A shared database lock protects that condition during concurrent changes.

The verification run found one administrator. Public signups create accounts with `administrator=false` and no application roles. Submitted admin/role fields cannot grant privileges. Only an authenticated existing administrator, using a CSRF-protected management request, can change administrative access.

## Move the local bootstrap account to your personal account

If the current local directory already exists, use the console to transfer administrative access deliberately.

1. Sign up with your own email and complete verification, or create your account from the Users screen.
2. While signed in as the current administrator, open your personal account in Users and enable **Directory administrator**.
3. Sign in with your personal account and confirm it opens the management console.
4. Remove **Directory administrator** from the original bootstrap account and disable that account if it is no longer needed.
5. Review **Administrators only** again and confirm your account is the only remaining administrator.

The one-time bootstrap marker prevents the original environment-configured account from being recreated or promoted on later restarts. Preserve a working administrator throughout the transfer.

## Public sign-up

The Sign in page links to **Create an account**, also available at `/signup`.

A signup enters a name, email, and password, then receives an email-verification link. Opening the link asks for the password chosen during registration. Verification links are hashed in storage, expire after 24 hours, and work once. This prevents someone with only a verification link from activating an account created with another person's password.

After verification, the user can sign in. Public accounts start with no application roles. Assign the appropriate roles from Users as needed. The **Resend verification email** flow supports pending accounts and limits new messages for the same email to one per minute.

Local development messages appear in [Mailpit](http://localhost:18125). Real-inbox delivery needs the SMTP settings in [DEPLOYMENT.md](DEPLOYMENT.md).

## Onboard another application

1. Open **Applications → Register application**.
2. Choose its application type.
   - **Public browser app** uses authorization code + PKCE and has no client secret.
   - **Confidential web app** keeps its secret on its server and supports code + PKCE and rotating refresh tokens.
   - **Service account** uses client credentials for the `api.read` scope in this version.
3. Enter a unique client ID, such as `billing-portal`, and the app's name.
4. Enter exact redirect URLs and post-logout redirect URLs for browser/web apps. For example, `http://localhost:5174/callback` during development and `https://billing.example.com/callback` after deployment.
5. Choose the required scopes. `openid profile email roles api.read` is a typical browser example. Add `api.write` when the protected API requires it.
6. Save the registration and copy any generated client secret to the application's server-side secret configuration.
7. Configure the application with Gatehouse's issuer and its registered client ID. Use OIDC discovery and an appropriate client SDK.
8. Assign application roles to users. Gatehouse administrator access is needed to manage registrations, and users can authenticate to applications with standard accounts.
9. Verify the integration using [INTEGRATION.md](INTEGRATION.md) and the included `/demo` application.

The local issuer is `http://localhost:18100`. Use a reachable HTTPS issuer for deployment. The receiving API validates the issuer, signature, audience, expiry, scopes, and any required application roles.
